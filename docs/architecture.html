📖 Overview

Arnis is a sophisticated Minecraft world generator that transforms real-world geographic data from OpenStreetMap (OSM) into accurate and detailed Minecraft worlds. The application supports both Minecraft Java Edition (1.17+) and Bedrock Edition, processing geospatial data to create realistic representations of terrain, buildings, roads, water bodies, and natural features.

🎯 Core Mission: Bridge the gap between real-world geography and Minecraft by providing an automated, accurate, and performant world generation pipeline that handles large-scale geographic data with ease.

Key Features

  • Real-World Accuracy: Uses OpenStreetMap data for authentic geography
  • Elevation Integration: Incorporates real terrain heights from AWS Terrarium tiles
  • Dual Edition Support: Generates worlds for both Java and Bedrock editions
  • Modular Architecture: Clean separation of concerns for maintainability
  • Performance Optimized: Parallel processing and efficient algorithms
  • User-Friendly GUI: Tauri-based desktop application with interactive map
  • CLI Support: Command-line interface for automation and scripting

Architectural Layers

1. User Interface Layer

Provides user interaction through both GUI and CLI interfaces. The GUI uses Tauri for a lightweight, native desktop experience, while the CLI offers powerful scripting capabilities.

  • GUI Module: src/gui.rs - Tauri-based web interface
  • CLI Module: src/args.rs - Command-line argument parsing
  • Progress Reporting: src/progress.rs - Real-time updates

2. Application Layer

Orchestrates the overall generation workflow, managing state and coordinating between layers.

  • Main Orchestrator: src/main.rs - Entry point and flow control
  • Data Processing: src/data_processing.rs - Generation pipeline
  • Configuration: tauri.conf.json, Cargo.toml

3. Processing Layer

Contains the core business logic for transforming OSM data into Minecraft structures.

  • OSM Parsing: src/osm_parser.rs - Data deserialization
  • Element Processing: src/element_processing/ - Feature generators
  • Map Transformation: src/map_transformation/ - Data preprocessing
  • Coordinate Systems: src/coordinate_system/ - Transformations

4. Data Access Layer

Handles interaction with external data sources and world file I/O.

  • Data Retrieval: src/retrieve_data.rs - API communication
  • Elevation Data: src/elevation_data.rs - Terrain heights
  • World Editor: src/world_editor/ - File management

5. External Services

  • Overpass API: OpenStreetMap data queries
  • AWS Terrarium: Elevation tile service
  • Nominatim API: Reverse geocoding for location names
⚠️ Rate Limiting: External APIs have rate limits. The application includes appropriate timeout handling and user-agent headers to be a good API citizen.

🧩 Core Components

🌐 Data Acquisition

Fetches geographic data from OpenStreetMap via Overpass API. Supports multiple download methods and includes robust error handling.

Module: retrieve_data.rs

📊 OSM Parser

Deserializes OSM JSON data into structured Rust types. Handles nodes, ways, and relations with their tags and relationships.

Module: osm_parser.rs

📐 Coordinate System

Transforms geographic coordinates (lat/lng) to Minecraft coordinates (x/z) with configurable scaling and projection.

Module: coordinate_system/

🏗️ Element Processors

Modular processors for different OSM features: buildings, roads, water, vegetation, and more. Each processor is independent and testable.

Module: element_processing/

🗺️ Map Transformation

Applies custom transformations to OSM data before generation. Configurable via JSON for flexibility.

Module: map_transformation/

⛰️ Elevation Data

Fetches and processes real-world elevation data from AWS Terrarium tiles. Applies smoothing and outlier filtering.

Module: elevation_data.rs

🌍 World Editor

Manages Minecraft world files. Supports both Java Anvil format and Bedrock LevelDB format with NBT serialization.

Module: world_editor/

🎨 Map Renderer

Generates 2D preview images of generated worlds. Creates top-down maps showing block colors for visual verification.

Module: map_renderer.rs

🎮 GUI Interface

Tauri-based desktop application with interactive map selection, settings configuration, and real-time progress tracking.

Module: gui.rs

🔄 Data Flow Pipeline

Generation Process

The world generation process follows a well-defined pipeline with seven main stages. Each stage is responsible for a specific transformation of the data.

[1/7] Fetching Data

Query Overpass API with bounding box

[2/7] Parsing Data

Deserialize JSON into Rust structures

[3/7] Transform Map

Apply custom transformations

[4/7] Processing Data

Route elements to processors

[5/7] Processing Terrain

Generate structures and features

[6/7] Generating Ground

Fill terrain layers and bedrock

[7/7] Saving World

Write region files to disk

Detailed Stage Breakdown

Stage 1: Data Fetching

The first stage retrieves OSM data for the specified bounding box. The system supports multiple download methods for flexibility and reliability. 

// Query
construction let query = format!("[bbox:{},{},{},{}];", bbox.min_lat, bbox.min_lng, bbox.max_lat, bbox.max_lng); // Download with timeout and retry logic let data = fetch_data_from_overpass(bbox, debug, downloader, save_file)?;

Stage 2: Data Parsing

Raw JSON is deserialized into structured Rust types. Coordinates are transformed from geographic (lat/lng) to Minecraft (x/z) coordinates. 

// Parse and transform
let (parsed_elements, xzbbox) = osm_parser::parse_osm_data(
    raw_data, bbox, scale, debug
);

// Elements are now in Minecraft coordinate space

Stage 3: Map Transformation

Custom transformations can be applied to preprocess the data. This is useful for filtering, translating, or modifying elements before generation.

Stage 4-5: Element Processing

Elements are processed by priority, ensuring correct layering. Each element type is routed to its specific processor module. 

// Priority-based processing
elements.sort_by_key(|e| get_priority(e));

for element in elements {
    match element {
        ProcessedElement::Way(way) => {
            if way.tags.contains_key("building") {
                buildings::generate_buildings(&mut editor, way, args, None);
            } else if way.tags.contains_key("highway") {
                highways::generate_highways(&mut editor, element, args, &connectivity);
            }
            // ... more processors
        }
    }
}

Stage 6: Ground Generation

After all features are placed, the ground layer is filled with grass, dirt, stone, and bedrock.

Stage 7: World Saving

Finally, all block data is serialized to region files in the appropriate format (Anvil or Bedrock).

✅ Performance Optimization: The pipeline uses parallel processing where possible, particularly in ground generation and element processing stages.

💡 Design Principles

1. Modularity

All components are cleanly separated into distinct modules with well-defined interfaces. Element processors are independent and can be developed/tested in isolation.

2. Performance First

The application is optimized for handling large geographic areas efficiently:

  • Early bbox clipping reduces memory usage
  • Parallel processing with rayon
  • Efficient data structures (HashMap for O(1) lookups)
  • Lazy evaluation where possible

3. Error Handling

Robust error handling throughout:

  • Result types for recoverable errors
  • Graceful degradation when possible
  • Informative error messages for users
  • Logging for debugging

4. Extensibility

New features can be added easily:

  • Add new element processors without changing core code
  • Custom transformations via JSON configuration
  • Plugin-friendly architecture

5. Cross-Platform Compatibility

The application runs on Windows, macOS, and Linux with platform-specific optimizations where needed.

✨ Future-Proof: The architecture is designed to accommodate future Minecraft versions and new OSM features with minimal changes to the core system.
